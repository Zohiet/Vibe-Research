按 Harness Engineering 规范开一个新 Goal。需求：**$ARGUMENTS**

先读 [`docs/harness/goal_workflow.md`](docs/harness/goal_workflow.md)，严格照它执行。

## 1. 先判档位

**按改动的性质判，不按碰了哪个目录判。**

| 档 | 什么算 | 怎么做 |
|---|---|---|
| **豁免** | 纯文档、错别字、注释、README 小修、无行为变化整理 | 不走闭环。告诉用户「这属于豁免」，直接做，提交信息里写明豁免理由 |
| **轻量** | 已有行为的修正：bugfix、依赖升级、重构 | 只写 Goal Spec，过第一道闸即可动手；验收判定追写在同一份文档末尾；直接在 dev 上做 |
| **完整** | 新行为：新功能、新端点、新页面、协议或数据格式变更 | 三份文档、两道闸、开 `goal/*` 分支 |

拿不准就用提交前缀反推：`docs/style/test`→豁免，`fix/chore/refactor`→轻量，`feat`→完整。
**偏离默认要说理由**（例：依赖升级挂 `chore:` 但有行为变化，应按完整档走）。

**别为了走流程而走流程**，也别为了省事把完整档压成轻量档——判错档位比判错方案更难发现。

## 2. 取编号、定 slug

```bash
ls docs/goals/ | sed -n 's/^VR-GOAL-\([0-9]\{3\}\).*/\1/p' | sort -n | tail -1
```

下一个三位编号，不复用、不回填。slug 用小写英文连字符。

**完整档**在这一步开分支并推上去（Goal Spec / Plan / 代码 / 验收报告全提在这条分支上）：

```bash
git checkout dev && git pull
git checkout -b goal/VR-GOAL-XXX_<slug>
git push -u origin goal/VR-GOAL-XXX_<slug>
```

轻量档不开分支，直接在 dev 上做。

## 3. 写 Goal Spec

照 [`docs/harness/templates/goal.md`](docs/harness/templates/goal.md) 写到
`docs/goals/VR-GOAL-XXX_<slug>.md`。

**重点在验收项。** 每条必须可判真假、**且写明证据形态**（截图 / 命令输出 / CI run URL /
文件片段）。写不出判据或证据形态的条目要么改写成可判定的，要么删掉。
「体验更好」「代码更清晰」不是验收项。

证据形态按改动性质选：有界面变化用截图，纯后端 / 基建改动用命令输出与 CI 链接——
**不要为了凑格式截一张无关的图。**

需求本身有歧义、或者切片明显太大（一句话说不完）时，**先问用户**，不要自己猜着填。

## 3.5 第一道闸：跑一轮拷打

**Goal Spec 写完就停，调用 `mattpocock-skills:grilling`**，把 Spec 里尚未拍板的
开放决策逐条质询到收敛。

**需求开放时先 brainstorming 再 grilling**（做法有多种、边界没想清的那种）；
需求明确、只剩取舍要拍板的，直接 grilling。

⚠️ **两者不能互相顶替。** brainstorming 是建设性的（往上搭方案），grilling 是
对抗性的（往下拆方案）。只搭不拆 = 方案没被攻过；只拆不搭 = 可能在攻一个方向
就选错的方案。**不要用「brainstorming 与 grilling 同等作用」这类话把它糊过去**
——那是本项目明令反对的「解释型通过」。

**不要退化成「把验收项摊出来请他确认」**——那是被动的是非题，扫一眼说「可以」就过了，
等于没有这道闸。真正的价值在于：本项目 VR-GOAL-001 / 002 的所有关键设计
（两道闸、三档分层、`--no-ff`、E2E 沙箱隔离）**没有一条是起草时想到的，全是拷打里定的**。

三条最容易违反的：

- **一次只问一个问题**，等回答再问下一个
- **每题给推荐答案**并说明取舍——让用户做选择题
- **能查到的是事实，自己去查**，别拿代码里能 grep 到的东西占用用户

收敛结论填进 Goal Spec 的「已收敛决策」表，把状态改成「验收项已确认（日期）」。

⚠️ **不要为了走流程制造问题。** 真没有可拍板的（单一解法的 bugfix 之类），
就在「已收敛决策」里写「无开放决策」+ 理由，直接往下走。**宁可零问题，
也不要五个凑数的问题**——那会消耗用户对这道闸的信任。

**轻量档到这里就可以开始实现了**（只有这一道闸）。完整档继续写 Plan。

## 4. 写实现 Plan

照 [`docs/harness/templates/plan.md`](docs/harness/templates/plan.md) 写到
`docs/plans/VR-GOAL-XXX_<slug>.md`。

逐面清单**不涉及的面写「不涉及」，不要删行**——删了就分不清是想过还是忘了。

风险那一节必须实际去查：改动的 API 有哪些调用方？
```bash
grep -rn "from \"@/lib/<模块>\"" frontend/src
```
本仓库最大的伤害源是 git 不报冲突的语义冲突，这一步不能省。

**「需要授权的动作」一节必须如实填**：改动他人写过的已有文件、装依赖 / 改环境、
删文件或删分支——这三类要显式列出来，确认 Plan 即视为授权。不涉及就写「无」，
**不要把这类动作藏在实施步骤里蒙混过关。**

## 5. 停下来等第二道闸

**写完 Plan 就停。不要开始写代码。**

把 Plan 的要点摘给用户看（尤其是风险和需要授权的动作），明确请他确认。
确认后把 Plan 里的「确认状态」改成 `✅ 已确认（日期）`，再开始实现。

这道闸门挡住的是「按错误口径实现完再返工」和「自作主张扩大范围」。
