# VR-GOAL-017 ｜ 资讯页切 tab 不再显示上一个 tab 的数据

- **状态**：验收项已确认（2026-08-03）
- **档位**：轻量（既有行为的修正，不新增端点 / 页面 / 数据格式）
- **创建日期**：2026-08-03
- **slug**：`intel-tab-data-bleed`
- **分支**：直接在 dev（轻量档）

## 背景

用户报告资讯页「A股公告」与「公开新闻」两个 tab **内容完全一致**，而且列表
**每隔几秒自动刷新一次、然后又恢复**——他以为是哪里混进了自动刷新（那个已剔出范围的功能）。

**没有任何定时器。** 全仓库的定时器只有两处：`useLiveQuotes`（10s，只用于关注股页）
与 `Portfolio.tsx`（30min）。资讯页一个都不沾。两个症状是**同一个 bug 的两面**。

### 根因（已确定性复现）

先排掉数据层：直接打两个端点，返回内容毫无重合——公告是 `date/title/type/url`，
新闻是六键中文契约，标题一条都不一样。**后端没问题。**

`Intel.tsx:353-358` 的渲染分支：

```tsx
{cur.key === "investment-news" ? <InvestmentNewsPanel />
 : cur.key === "filings"       ? <WatchlistFeed kind="filings" />
 : cur.key === "news"          ? <WatchlistFeed kind="news" />
 : <>…</>}
```

后两个分支是**同一个组件类型、占同一个子位置、没有 `key`**。React 的 reconciliation
判定「同一个实例、只是 props 变了」→ **不重挂载**，`rows` state 原样留着。

叠加第二个缺陷：`load()`（`Intel.tsx:223-271`）**没有任何取消或时序守卫**，
promise 一落地就无条件 `setRows`——上一个 tab 遗留的请求照样能盖掉当前 tab。

### 实测复现（page.route 打桩，两边给不同标题 + 2.5s 延迟，不碰网络）

```
① 公告 tab 已出数据
② 刚切到新闻 tab，公告内容还在？ true
   顶部计数： 关注 1 只 · 共 1 条新闻（近期）     ← 标签写着"新闻"，列表里是公告
③ 几秒后新闻数据到达，列表内容被替换              ← 用户说的"自动刷新"

④ 停在「A股公告」tab，此时新闻请求仍在飞
   t≈1.0s  公告=false 新闻=true                  ← 迟到的新闻响应盖进了公告 tab
   t≈2.5s  公告=true  新闻=false                 ← 用户说的"又恢复"
   t≈4.0s  公告=true  新闻=false
```

②那行还暴露一个加重因素：**连转圈都不给**。加载态条件是 `loading && rows.length === 0`，
而 rows 非空（上一个 tab 的），所以界面上没有任何"正在加载"的信号——
上一个 tab 的数据看起来就是这个 tab 的真数据。

延迟实测用的 2.5s；**真实使用下更久**：`em_get` ≥1s 串行限流，关注 N 只股票
一次 load 要 N 秒以上，两个 tab 的请求在同一条队列里排，重叠窗口很长。

### 这不是 VR-GOAL-016 引入的

`git log -L 216,275 / 353,359` 显示这段代码**自 2026-07-05 首次发布起未被改动过**。
但 016 是它变明显的原因：016 之前 `/api/news` 对每个代码都 502，新闻 tab 必然落到空列表，
串味只闪一下就变成「暂无新闻」；016 修好之后两边都有数据，串味才呈现成「两处一模一样」。

### 仓库里已有的正确做法

`StockData.tsx:106` 有现成的竞态守卫 `runIdRef`（注释：「快速换代码时只让最新一次回填」），
每次 `run()` 自增，回填前比对 `rid === runIdRef.current`。**Intel 没用这套。**

## 已收敛决策（拷打于 2026-08-03）

| # | 议题 | 裁决 | 理由 / 取舍 |
|---|---|---|---|
| 1 | 修到多深 | **只加 `key={kind}`，不加竞态守卫** | 实测 `key` 单独一条即可消掉两个症状。同 tab 内并发 load **发生不了**（`Intel.tsx:291` 刷新按钮 `disabled={loading}`），加守卫就是加一段永不进入的分支——`CLAUDE.md`「从不执行的代码就是 bug 藏身处」。守卫防的那个假想改动真发生时，验收项 1/3 的回归测试本来就会变红 |
| 2 | 「切 tab 要重拉」治不治 | **治，但治在后端** | ⚠️ 起草时我量化成「每切一次等 13 秒」，**是错的**：`app.py:640` 的 `_ANN_CACHE` 早有 15 分钟缓存，公告 tab 秒回。这批端点里**只有 `/api/news` 漏了缓存**（VR-GOAL-016 重写它时只管修 502，没对齐邻居）。用户要的「后端不关就还在」= 进程内存缓存，仓库到处都是这个模式，补漏即可 |
| 3 | 前端要不要也缓存一份 | **不要** | 系统已有缓存层，再叠一层就是两处缓存、两套失效规则，以后对不上要查两遍。前端保持无状态，切页面回来照常请求、后端秒回。也不走 `aisession`——`CLAUDE.md:172` 写死「只存 AI 产出，UI 状态不要放进来，端点特意叫 `aisession` 而不是 `uistate`」 |
| 4 | 刷新按钮怎么办 | **让它穿透缓存**，照 `/api/radar/refresh` 的形状 | 拷打里挖出来的既有毛病：公告 tab 的「刷新」**15 分钟内点了纹丝不动**，今天就是这样，只是被串味掩盖了。一个点了不干活的按钮比没有按钮更糟。代价诚实记：穿透后每只股票重排 ≥1s 队列，点一次真的要等 N 秒——但这正是「人手点才重拉」要的语义 |
| 5 | `/api/news` 的 TTL | **15 分钟**，与 `/api/announcements` 对齐 | 同一页面上的两个 tab 若用两个 TTL，「为什么这个变了那个没变」就解释不了 |
| 6 | 个股页的「查询」要不要也穿透 | **不要** | 它的语义是"查这只股票"不是"重抓"；一次要拉 15+ 个端点，全穿透会把限流队列彻底堵死（本来就 12~16 秒）。且个股页对公告**今天就是这个行为**，新闻跟上只是对齐 |
| 7 | 三件事要不要拆成多个 Goal | **不拆** | 照 VR-GOAL-015 先例：轻量档不开分支、没有合并点，三件事本来就是三个独立提交，撤哪个都是一条 `git revert <sha>` |

## 不在范围内

- **`em_get` 的 ≥1s 串行限流本身**——那才是「个股页 12~16 秒」的真瓶颈，要治得改并发
  （分域名令牌桶之类），风险等级高。已是 backlog 第一条，单开 Goal。
- **个股页「查询」的缓存穿透**（决策 6）。
- **前端任何形式的缓存**（决策 3）。
- **竞态守卫 `runIdRef`**（决策 1）。
