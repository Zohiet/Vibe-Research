## 背景

持仓页现在有三个问题，都源于**「持仓」和「已清仓」是两套互不联动的操作**：

1. **减仓功能根本不存在**。没有任何 API 能减少股数，只能 `remove_holding` 整笔删掉、再 `add_holding` 添回剩余股数——而且要原样重填加权成本，填错一点后面所有盈亏就不准了。
2. **`close_position` 只往 `closed` 追加记录，从不碰 holdings**。卖出后必须手工维护两边。
3. **加仓不留任何痕迹**，与卖出记录不对称。

真实数据印证了这个痛点：`688253`（英诺特）同时出现在持仓（1795 股）和已清仓（2516 股）里，`588170` 也是——都是部分卖出后手工维护两边的产物。

第 3 条还藏着一个洞：**加仓填错了无法干净撤销**。唯一办法是减仓，但减仓会记一笔卖出并计入已实现盈亏——一笔根本没发生的交易污染了盈亏历史。

## 垂直切片

- **角色**：记账的投研用户
- **动作**：在持仓明细的行内直接加仓 / 减仓
- **可见结果**：股数与加权成本自动更新，同时生成一条可撤销的交易流水；不再需要手工对账

| 3 | 交互形态 | **行内展开**（点按钮，行下方展开表单） | 操作时能同时看到该行的现价/数量/成本，弹窗会盖住；`Notes.tsx` 已有同款展开模式可照抄；省掉弹窗的焦点管理与遮罩处理 |
| 4 | 买卖记录是否合成一张表 | **合成 `transactions` 流水表**，持仓仍单独存 | 用户提出。修掉了「加仓无法干净撤销」的洞；买卖对称。**不做彻底事件溯源**——已有持仓的买入历史在数据里根本不存在，无法迁移，只能伪造 |
| 5 | 撤销机制 | **每笔交易存操作前的持仓快照，撤销 = 写回快照**；限制为「该代码的最新一笔」 | 快照还原精确，避免反推加权平均的浮点漂移。副产品：历史 7 条无快照，天然不可撤销，**撤销条件统一成一条规则**（有快照 && 是最新一笔），不需要 `from_reduce` 之类的来源标记，前端也不用加「来源」列 |

| # | 议题 | 裁决 | 理由 / 取舍 |
|---|---|---|---|
| 6 | **🗑 删除持仓会让撤销「复活」已删的仓位**（真 bug） | **🗑 只在该代码没有可撤销流水时才显示** | 快照式撤销隐含假设「这笔交易之后持仓没被别的途径改过」，而 `remove_holding` 恰恰不写流水。复现路径：减仓 40 → 🗑 删掉剩余 → 撤销减仓 → 凭空复活 100 股。🗑 在本次改造后的真实职责只剩「删除那 4 条无流水来源的历史持仓」，按职责收窄显示条件即可，比加运行时守卫或引入 `type:"remove"` 新概念都干净 |
| 7 | 迁移失败会静默丢数据 | **迁移失败则拒绝所有持仓写操作**（HTTP 503 + 说明），读操作用旧结构降级展示 | 这次迁移改的是**文件内容结构**，不是像 `_migrate_legacy` 那样搬文件位置。失败后若照常启动：新代码读不到 `transactions` → 用户以为记录为空 → 随手加一笔 → `_save` 按新结构写回 → 旧的 7 条永久消失。备选「永久双读兼容」会留一个谁碰谁都要想一遍的分支，一次性迁移不值得付永久成本 |
| 8 | `Portfolio.tsx` 已 304 行装了 6 件事 | **抽 `HoldingRow.tsx` + `TransactionList.tsx`**，只拆本 Goal 要碰的两块 | 本 Goal 净增约 110 行 → 450+。行内展开的状态（哪行展开、表单内容、实时盈亏）天然属于行，放进 `HoldingRow` 可省掉页面级一堆 `useState`；组件边界清晰后 E2E 选择器也不用再靠 `div:has(> h3:...)` 猜 DOM。先例：`components/ui/EarningsSnapshot.tsx` 就是从个股页抽出来的整块。**不做本 Goal 之外的重构** |

补充口径（收敛过程中一并定下，无争议）：

- 卖出价默认填当前现价、可改；日期默认今天、可改
  - ⚠️ **日期可改只是为了补记时间，不追溯历史成本**：盈亏一律按**当前**加权平均成本算。
    把它当"补录三个月前的交易"用会算错——那时的成本和现在不是一回事
- 加仓表单只有股数 + 买入价，无日期字段（不产生已实现盈亏）
  - 但**也给预览**：显示「加仓后成本变为 X」。不产生盈亏，却会摊薄成本，当场看得见比事后发现好
- **撤销 buy 时若 `prev_shares == 0`**（即那笔是新建仓）→ 删除整条持仓，不留 0 股的空记录
- 「已清仓」列表改名 **「交易记录」**；撤销按钮文案用「撤销」不用「删除」
- 已有 4 条持仓在流水里没有对应 buy 记录，**不伪造**，列表顶部注明「流水自 2026-07-30 起记录」
- 行内 🗑 删除按钮保留——语义是「这条记录本身是错的」，与减仓（真的卖了）不同

## 设计

### 数据模型

```jsonc
{
  "holdings": [{ "code", "shares", "cost" }],   // 结构完全不变
  "transactions": [{
    "id",                                        // 删除用 id，不用 index
    "code", "name", "date",
    "type": "buy" | "sell",
    "shares", "price",
    "prev_shares", "prev_cost",                  // 操作前的持仓快照；迁移来的历史记录无此字段
    "pnl", "pnl_pct"                             // 仅 sell 有
  }]
}
```

### 后端

| 端点 | 变化 |
|---|---|
| `POST /api/portfolio/holding` | 加仓。加权平均合并逻辑不变，**额外写一条 `type:buy` 流水 + 快照** |
| `POST /api/portfolio/reduce` | **新增**。入参 `{code, shares, price, date}`；后端自取加权成本；减到 0 移除持仓；写 `type:sell` 流水。全程在既有 `_LOCK` 内一次 `_save` |
| `DELETE /api/portfolio/transaction/{id}` | **新增**，撤销 = 把 `prev_shares/prev_cost` 写回持仓 |
| `GET /api/portfolio` | 返回字段 `closed` → `transactions`；`realized_pnl` 只从 `type:sell` 累加 |
| `POST /api/portfolio/close` | **删除**。「添加清仓记录」表单已去掉（决策 #2），此端点无调用方 |
| `DELETE /api/portfolio/close` | **删除**。由 `/transaction/{id}` 取代 |

**「最新一笔」的判定**：按 `transactions` 数组中该 `code` **最后出现的那条**（追加顺序），
不按 `date` 字段——同一天可能有多笔，日期分不出先后。

**交易记录列表排序**：按数组顺序**倒序**展示（最新在上）。

**为什么减仓必须是一个端点**：它是双写（改 holdings + 加流水）。拆成两次调用，中间失败就是数据不一致——而「不用手工对账」正是本 Goal 的立意。

**迁移**：把旧 `closed` 转成 `transactions`（补 id、`type:"sell"`、不补快照）。

- **在 import 时跑一次**，照 `portfolio.py:46` 现有 `_migrate_legacy()` 的模式。
  **不放在 `_load()` 里**——那是纯读路径，被 `get_portfolio()` 和每半小时的定时刷新调用，
  在里面写文件会让读操作产生副作用。
- 先写 `portfolio.json.bak-<YYYYMMDD-HHMMSS>`（不删除，留给用户处置），
  再用 `tmp + os.replace` 原子落位——要么完整落地，要么原文件纹丝不动。
- **失败则置一个模块级标志**：`/api/portfolio` 的所有写端点返回 **HTTP 503**
  「数据迁移未完成，为防丢失已暂停写入」；读端点用旧 `closed` 结构降级展示。
  失败原因打 stderr。**绝不允许在未迁移成功的数据上执行写入。**

### 前端

行内 `[加仓] [减仓]` 按钮 → 行下方展开表单，边填边算「本次已实现盈亏」。股数超过持仓时确认按钮禁用；减到 0 时提示「将清空该持仓」。

「交易记录」列表加类型列，显示买/卖两种；不可撤销的记录不显示撤销按钮；确认框写明「将还原 100 股持仓（成本 1,500）」。
