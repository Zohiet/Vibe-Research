| 症状 | 真相 | 为什么没早发现 |
|---|---|---|

## 实测到的事实

**① 辩论：单个角色失败会污染最终产物，且不留痕**

`debate.py` 的失败处理是对的一半、错的一半：

```python
except Exception as e:
    yield {"type": "error", ...}
    yield {"type": "stage_done", ..., "failed": True}
    continue          # 失败内容不进 transcript —— 这一半是对的
```

不把错误信息当论据喂给下游，对。**但后果是主持人拿到「多方陈述 + 空方陈述 + 多方反驳」，
唯独少了空方反驳——它在总结一场「多方反驳了、空方没反驳」的辩论，而它并不知道少了一块。**

一次外部抖动，污染的是最终产物，**且看不出被污染**。

**② 这次失败是外部的、间歇的，不是代码 bug**

A/B 实测（每组 3 次，共 6 次；另加一场完整的二轮辩论 5 次调用）：

```
带 MCP    #1 rc=0 24s   #2 rc=0 18s   #3 rc=0 20s
屏蔽 MCP  #1 rc=0 18s   #2 rc=0 21s   #3 rc=0 22s
```

**11 次调用 0 次失败** —— 复现不出来。「是不是排查中挂上的 MCP 导致的」这个怀疑**被证伪**。
按 systematic-debugging 的规定，查到这一步该改为「实现适当的处理（重试）」而非继续追因。

**③ 日志：今天三次排查全卡在这**

- `ci.ps1` 起沙箱时重定向到 `.sandbox-data/ci-backend.log`（**有日志**）
- `dev.ps1` 起的日常实例只打在窗口里（**没有日志**）

**最需要日志的恰恰是日常实例**（真实数据、真实使用），结果只有它没有。
第三次排查时，我为了拿一个 traceback **不得不绕开启动脚本、自己另起一个带重定向的进程**。

窗口输出还有两个隐性损耗：**scrollback 有上限**、**关窗口就全没了**。

**④ 资讯雷达：不刷新就永远是旧的，且缓存放错地方**

```python
CACHE_DIR = os.path.join(HERE, ".cache")   # HERE = backend/ —— 在仓库里
def get_radar(force=False):
    if force: return fetch_radar()
    return load_cache() or skeleton()      # 从不自动刷新
```

实测 `backend/.cache/radar.json` 时间戳 **7-31 11:13**（当天是 8-1）。两个后果：

- **不点「刷新」就永远显示上次抓取的结果**
- **缓存不遵守 `VR_DATA_DIR` 隔离** —— 沙箱与真实实例**共用同一份**。
  E2E 跑一次刷新就会改掉用户日常看的数据，违反 `CLAUDE.md` 的「用户数据都在 `~/.vibe-research/`」红线

> ⚠️ **起草时写的「页面也不说它是哪天的」是错的，核查后删除。**
> `Intel.tsx:101` 已经渲染「更新于 {generated_at}」，后端 `fetch_radar()` 也一直在写这个字段。
> 真正缺的是**旧了没有任何显眼提示**——「更新于 7-31」和「更新于今天 09:00」长得一模一样。

## 已收敛决策（拷打于 2026-08-01）

| # | 议题 | 结论 | 理由 |
|---|---|---|---|
| 1 | 三件事合不合 | **合成一个 Goal、轻量档**，但把「雷达自动刷新」踢出范围 | 草案给的拆分理由（「捆一起撤不掉」）**站不住**：轻量档不开分支、没有合并点，三件事本来就是三个独立提交，撤哪个都是一条 `git revert <sha>`。真正决定拆不拆的是档位——而只有「自动刷新」够得上完整档（新行为、定时打 108 个源），剔掉它其余全是轻量 |
| 2 | 日志怎么落 | **后端自己写**：`logging` + `RotatingFileHandler`（5MB × 3）→ `VR_DATA_DIR/logs/`，**窗口输出保留**（同时挂 StreamHandler）| `ci.ps1` 那套脚本重定向已经用事实证明「靠启动脚本」只覆盖一种启动方式——沙箱有日志、日常实例没有，正是本 Goal 的起因。再写一次同形状的东西只是把盲区从「日常实例」挪到「手工起的实例」（而 `CLAUDE.md` 明确教用户手工 `uvicorn app:app` 跑）。且 uvicorn 的 access/error logger 本来就在 `logging` 上，不用新写任何 log 语句就能拿到那些行 |
| 3 | 重试几次 | **重试 1 次，且超时不重试** | 区分两种失败：**快速失败**（`退出码 1`，几秒回来）重试几乎免费且很可能成功；**超时失败**（跑满 300s）重试要再赔 300s，而跑满超时通常意味着这次请求本身有问题。二轮辩论 5 阶段 × 300s = 最坏 25 分钟，本方案**不给最坏情况加任何时间** |
| 4 | 缺席告诉谁 | **告诉所有后续角色**，措辞照抄底稿的「数据缺口」→ `## 本场缺席\n以下角色本轮未能发言，不得假装其已表达：…` | 草案把这题定窄了。`bull_rebut` 的提示词第一句就是「**上面是空方的质疑**。逐条回应」——空方缺席时这句话是假的，模型会对着不存在的质疑编回应。**污染发生在反驳轮，比主持人误判更早、更严重**；主持人拿到的是「看起来完整的假发言」。代码量与只告诉主持人相同（同在 `_build_messages` 里）|
| 5 | 陈旧提示怎么做 | **抽出 `AiStamp` 的相对时间格式化为共用 helper**，雷达头部用它（「3 天前 07-31 11:13」+ 跨天变色）。**只抽函数、不搬组件** | VR-GOAL-010 已经踩过「按日历日算差、不按 24 小时」那个坑，不重踩。但 `AiStamp` 组件语义是「AI 产出时间戳」，整个拖到雷达上会让它退化成万金油 |

### 不需要拍板的（查证后即定，记在这里免得再问）

- **旧雷达缓存 `backend/.cache/radar.json` 不做迁移。** `portfolio` / `myreports` /
  `myaccumulation` 有 `_migrate_legacy()`，是因为那是**用户手写的、丢了就没了**；
  雷达缓存是**抓来的派生数据**，点一次刷新就回来。为不可再生数据设计的搬运仪式
  套到可再生数据上，只是多一段没人会验证的代码。
- **迁进 `VR_DATA_DIR` 后自动获得测试隔离**：`conftest.py` 已设 `VR_DATA_DIR` 指向临时目录。
- **没有 E2E 依赖雷达数据**（`grep` 全仓库 e2e 无命中），迁移不会打断现有验收脚本。

## 实现中发现的问题（Spec 没预料到的）

**① 日志写了两遍——靠证据抓出来的，不是靠测试。**
第一版把同一个 handler 既挂 root 又挂每个 uvicorn logger，理由是「uvicorn 会把
`propagate` 设成 False」。**实测这版 uvicorn 并没有设**，于是每条日志写了两遍。
是「真起一次后端 `cat` 日志」那一步当场看到的——单测当时全绿。
改成只挂 root + 显式开 `propagate`（两种情况下都恰好一份），并补了
`test_no_duplicate_lines` 盯住它。

> 这条值得记：**验收项 6 我写的是「含启动行与请求行」，重复写两遍完全满足这条判据。**
> 是「打开看一眼」而不是「断言通过」发现的问题。

**② 「已经吐过字的不重试」是 Spec 之外补上的约束。**
拷打时只定了「超时不重试」。实现时发现流式路径可能吐了半截才失败——那时重试会让
第二遍文本接在半截后面。要干净重来得加「清空该阶段」的协议事件并改前端，超出本 Goal 范围。
于是 `_retriable` 加了第二个条件，并写了 `test_partial_output_is_not_retried`。
**目标失败形态（CLI 一次性返回）失败时缓冲必为空，这条不影响覆盖面。**

**③ 顺手清了自己刚引入的 deprecation warning。**
`@app.on_event("startup")` 在当前 FastAPI 上已废弃、跑测试会告警两条。改用 `lifespan`。
不留「反正只是 warning」的债。

**④ 为了让「超时」可判定，给 `cli_runtime` 新立了 `CliTimeout` 类型。**
原先超时只体现在错误**字符串**里（`RuntimeError("…生成超时…")`），按文案匹配会在改文案那天
静默失效。`test_is_timeout_judges_by_type_not_text` 用 5 种异常参数化盯住。
