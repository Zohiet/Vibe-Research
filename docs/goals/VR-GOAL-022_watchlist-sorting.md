## 背景

自选股页现在按**加入顺序**渲染（`Watchlist.tsx:199` 的 `codes.map`，`codes` 来自
`loadWatch()` 的持久化顺序），表头是一个纯静态数组（`:191`）。

自选股一多，"今天谁涨了 / 谁在放量"就得一行行扫。用户要求按**涨跌**和**换手**排序。

两个已经查明的前提：

1. **数据全都是现成的**。`quotes[code]` 里已有 `change_pct` 与 `turnover_pct`
   （`api.ts:114` 的 `Quote`），纯前端排序，**不用碰后端**。
2. **仓库里没有任何用户可控的排序先例**。全库只有两处 `.sort()`
   （`Intel.tsx:265` 按时间、`MyReports.tsx:79` 分组），都是写死的、用户点不动。
   所以本 Goal 顺带**立一套可排序表格的样式**，后面的页面照抄。

一个必须在设计里正面处理的张力：**开着实时行情时是 3 秒一拍**
（`useLiveQuotes.ts:LIVE_INTERVAL_MS`）。按涨跌排序意味着行会随行情跳动而重排——
你正要点某一行，它可能已经换了位置。这不是实现细节，是产品决定。

## 垂直切片

- **角色**：使用自选股页的投研用户
- **动作**：按涨跌幅或换手率给自选列表排序
- **可见结果**：表格立刻按该列重排，且能看出当前按哪列、哪个方向排

## 验收项

| # | 验收项 | 判据 | 证据形态 |
|---|---|---|---|
| 1 | 能按涨跌排序 | 用固定行情桩数据，触发按「涨跌%」排序后，读表格各行的涨跌值，断言**单调不增** | E2E 断言 + 截图 |
| 2 | 能按换手排序 | 同上，按「换手%」排序后各行换手值**单调不增** | E2E 断言 + 截图 |
| 3 | 能切换升 / 降序 | 再次触发同一列后，各行值**单调不减** | E2E 断言 |
| 4 | 当前排序状态看得见 | 排序中的列有可判定的视觉标记（`aria-sort` 属性 + 方向图标），未排序的列没有 | E2E 断言（读 `aria-sort`）+ 截图 |
| 5 | 行情未取到的股票不污染排序 | 桩数据里留一只没有行情的代码，断言它**固定排在末尾**，且升降序切换时**仍在末尾** | E2E 断言 |
| 6 | 排序不改变持久化的自选顺序 | 排序后读 `localStorage` 的自选列表，断言与排序前**逐项相同**——排序是"看"的方式，不是"改"数据 | E2E 断言 |
| 7 | 全套验证通过 | `./ci.ps1 -E2E` 全绿；GitHub Actions run 绿 | 命令输出 + Actions run URL |

> **判据自检**：
> - **无时序污染**：七条都在实现完成当场可验，不依赖「合并后 / 发布后」。
> - **无度量污染**：判据是**排序后序列的单调性**与 `aria-sort` 属性值，
>   不是"多少列可排"这类会被本 Goal 自己搅动的计数。
> - ⚠️ **判据不能依赖真实行情**：真实涨跌每 3 秒变一次，断言"第一行是某某"明天必红。
>   所以验收项 1/2/3/5 一律用 `page.route` 打桩固定行情，**只断言顺序关系、不断言具体数值**——
>   这与本仓库既有 E2E 的纪律一致（`expectNumericLike` 只验形状不验值）。

## 已收敛决策

> 第一道闸（拷打，2026-08-06）的产物。

| # | 议题 | 裁决 | 理由 / 取舍 |
|---|---|---|---|
| 1 | 交互形式 | **点表头**（`<th>` 变按钮 + `aria-sort`），**所有数值列可排**（现价 / 涨跌% / PE(TTM) / PB / 换手%）；名称 / 代码 / 操作列不可排 | 通用心智、零学习成本，且 `aria-sort` 是**现成的可判真假判据**，比"看截图上有没有箭头"硬得多。本仓库没有任何可排序表格先例，本 Goal 等于立样式，就该立通用那种。规则简单到不用解释：**数字能排，文字不排**——只放开涨跌与换手反而要多写一句解释，而代码是同一份 |
| 2 | 开着实时行情时要不要跟着重排 | **跟着重排** | 顺序永远是真的。否决"快照式"：那会造成表头写着 ▾ 降序、实际已不是降序——**宁可跳，不可说谎**。否决"悬停冻结"：体验最好但引入悬停状态机，且与 3 秒轮询有竞态，**写出来的测试会是不稳定的那种**。残余风险（换位瞬间点到「移除」）需要"开实时 + 交易时段 + 恰好那一瞬"三条同时成立，且删除是可见的、不是静默损坏；实时行情本身默认关闭（`Watchlist.tsx:40`） |
| 3 | 默认排序 | **默认「加入顺序」**（现状）；点第三次回到加入顺序；**首次点击一律降序**，第二次升序 | **这是合规决定**：用户主动点是他自己选的查看方式；默认排成涨幅榜则是产品替他做了"今天该关注谁"的排序。本产品定位是「只配数据、不给结论」，**默认视图恰恰是最容易夹带结论的地方**。另外"加入顺序"本身有信息——用户常按赛道成批粘贴，那是他的组织方式，不该被默认覆盖。首次点击不做按列定制（如"PE 首次给升序"），否则要解释"为什么这列反着来" |
| 4 | 排序偏好是否持久化 | **记住**（`localStorage`，走 `@/lib/storage`） | 与仓库既有做法一致：实时开关 `vr-watchlist-live`、侧栏 `vr-sidebar`、主题 `vr-theme` 全都记住。**且不削弱决策 3 的合规论据**——默认排序是产品替用户决定，记住用户点过的选择是尊重他。关键在于**可见性把持久化变安全了**：表头必须显示当前排序状态（验收项 4），用户一打开就知道"是我上次按涨跌排的"，不会出现"我的加入顺序哪去了"。这两条是配套的，不能只做一半 |
| 5 | 行情未取到的股票排哪儿 | **固定沉底**，升降序都在末尾 | 它们没有可比较的值，塞进排序只能假装成 0 或 -∞ ——**"不返回假的 0"是 VR-GOAL-014 定过的规矩** |

## 不在范围内

- **后端排序 / 分页**——数据量是个人自选（几十只），前端排足够。
- **多列组合排序**（先按涨跌再按换手）——没有需求，且交互复杂度陡增。
- **持仓页 / 板块页的排序**——本 Goal 只做自选股页；样式立好之后另说。
- **拖拽手工排序**——与"按数据排序"是两件事。
